# Как проектировать задачи

## Главный принцип

Каждая задача — маленький кусок реальной backend-работы, завёрнутый в
короткую легенду. Ученик решает ту же алгоритмическую задачу, что и на
курсе, но в постановке, которую он потом встретит в вакансии и на
собеседовании. Абстрактное «переверните строку» → реальное «нормализуйте
slug для URL статьи».

## Структура файла задачи

```python
"""
Задача: <название>
Тема: <тема из known_topics.md>  |  Сложность: <0-10> (<прилагательное>)

Легенда: <2-4 предложения: где в backend такое встречается>

Вход:  <что принимает функция>
Выход: <что возвращает>

Примеры:
    <вход> -> <выход>
    <вход> -> <выход>  (граничный случай)
"""


def solve(...):
    pass
```

Имя функции — осмысленное (`normalize_slug`, `parse_log_line`), не `solve`.

**Ранний выход из чтения ввода —писать в условии явно.** Если правильное
решение может завершиться, не дочитав весь ввод (`break` по первому
совпадению, выход по условию), в блоке «Вход» отдельной строкой сказать:
программа читает ровно столько строк, сколько запросит, и вводить остаток
не нужно. Иначе ученик, проверяя руками, упирается в то, что программа
«не даёт» ввести оставшиеся строки, и считает это ошибкой своего кода
(2026-08-06, «Первая ошибка в логе выкатки»). То же касается примеров: у
входа с ранним выходом пометить, какие строки при таком вводе фактически
не читаются.

## Банк сценариев по этапам roadmap

**Строки (текущий этап):**
- парсинг строки лога: вытащить уровень (`ERROR`/`INFO`), время, сообщение;
- валидация username/email по правилам (длина, допустимые символы);
- нормализация slug для URL (пробелы → дефисы, нижний регистр);
- маскирование данных: телефон/карта → `+7***1234`;
- подсчёт слов/символов для превью статьи, обрезка с `...`;
- проверка палиндрома в постановке «дедупликация поисковых запросов».

**Списки/словари (следующий этап):**
- агрегация: топ-N ошибок из списка логов;
- группировка заказов по статусу;
- дедупликация email-рассылки с сохранением порядка;
- «конфиг из строк вида key=value → словарь».

**Функции/исключения:**
- валидатор входных данных API, бросающий понятные исключения;
- retry-обёртка «повтори N раз».

**Файлы:**
- чтение CSV-выгрузки заказов и подсчёт выручки;
- ротация: разбить большой лог на файлы по дате.

Дальше по roadmap (ООП, SQL, FastAPI) — придумывать сценарии в том же духе:
модель заказа, репозиторий, эндпоинт.

Банк можно пополнять реальными сюжетами с рынка (вопросы и тестовые с
собеседований junior Python backend РФ) через web-research skill
(`study_python/research-skill/`) — по запросу пользователя или при входе
в новый этап roadmap. Из интернета берём **сюжеты**, не готовые задачи:
калибровка под уровень остаётся за known_topics.md. Новые сценарии
вписывать сюда после подтверждения пользователя.

## Сложность

Сложность — не свойство задачи «вообще», а её **трудность именно для этого
ученика прямо сейчас**. Поэтому считается **относительно** `known_topics.md`
по шкале **0–10** и **пересчитывается** (не замораживается — см. ниже).

**Как считать.** Сложить четыре слагаемых и обрезать в диапазон [0, 10]:

1. **Композиция** — сколько разных приёмов надо совместить в одном решении:
   1 приём → 1, 2 → 2, 3 → 3, 4 и больше → 4.
2. **Незакреплённость** — за каждый требуемый приём, глядя в `known_topics.md`:
   из блока 1 «уверенно владею» → +0; из блока 2 «видел, не закреплено» → +1;
   из блока 3 «не трогал» → +2 (но такие приёмы задача вообще не должна
   требовать — см. Режим 1).
3. **Новизна паттерна** — насколько нов сам ход мысли: знакомый → +0; новый
   приём вроде «бегущий максимум с запоминанием слова-победителя» → +2;
   многошаговый незнакомый алгоритм → +3.
4. **Граничные/«грязные» данные**, которые надо явно обработать (пустой вход,
   регистр, лишние пробелы): нет → +0; есть → +1..+2.

**Прилагательное для показа** (сайт, докстринг): 0–2 — лёгкая, 3–5 — средняя,
6–7 — сложная, 8–10 — очень сложная.

**Затухание (обязательно).** Оценка привязана к текущим знаниям, поэтому по
мере обучения та же задача становится легче. Пересчитывать сложность:
(1) при генерации новой задачи (Режим 1/5); (2) при любом обновлении
`known_topics.md` — когда приём переходит из блока 2→1 или 3→2→1, слагаемые
за незакреплённость и новизну падают. При обновлении known_topics **пройтись
по активным записям `practice_queue.json` и пересчитать их `difficulty`**,
чтобы на сайте не висела «сложная» тема, которую ученик уже освоил.

**Ориентиры для калибровки.** 0–2 — одна изученная конструкция, 3–6 строк
(новые темы, повторения после сбоя). 3–5 — две-три конструкции вместе +
граничные случаи (основной рабочий уровень). 6–8 — мини-фича целиком
(парсер + валидация + агрегация) или заметно новый паттерн; давать, когда по
теме стабильные 4-5. 9–10 — держать в резерве, почти всегда сигнал, что
задача требует ещё не пройденного.

## Тесты

5-8 штук: типовой случай, пустой вход, граничные значения, «грязные» данные
(лишние пробелы, регистр). Пока pytest не пройден на курсе — оформлять так,
чтобы работало и через `python test_x.py`:

```python
from slug import normalize_slug


def test_basic():
    assert normalize_slug("Hello World") == "hello-world"


if __name__ == "__main__":
    test_basic()
    ...
    print("Все тесты прошли!")
```
