# Web Research

Один принцип: интернет — последний уровень, а не первый. Каждый платный
запрос должен переживать сессию — результат обязан осесть в кэше.

## Когда веб-поиск НЕ запускать

- Факт стабильный: синтаксис, stdlib, PEP8, алгоритмы, педагогика.
- Ответ уже есть в локальных файлах проекта или памяти.
- В кэше `study_python/research/INDEX.md` есть запись по теме с живым TTL.

Хотя бы одно верно — отвечать без интернета и сказать пользователю,
откуда взят ответ (кэш такой-то от такой-то даты / знания модели).

## Порядок инструментов (сверху вниз, ниже — только при неудаче выше)

1. **Кэш** `research/INDEX.md` — тема уже исследована и свежа?
2. **`gh` CLI** — всё про GitHub: релизы `gh api repos/OWNER/REPO/releases`,
   issues, код. Скрейпить GitHub через интернет — запрещено, API точнее
   и бесплатен.
3. **WebFetch** — известен точный URL статичной страницы
   (docs.python.org, PEP'ы и т.п.).
4. **Firecrawl `search`** — нужен именно поиск. Сразу с контентом
   (`--scrape`), `--limit 3-5`, свежесть через `--tbs qdr:y`.
5. **Firecrawl `scrape`** — конкретная страница, которую WebFetch не взял
   (JS-рендеринг, антибот: hh.ru, часть блогов).
6. **Firecrawl `map` + выборочный `scrape`** — несколько страниц одного
   сайта (конспект по разделу документации): сначала map со `--search`,
   выбрать 5-10 нужных URL, скрейпить только их.
7. **Firecrawl `crawl`** — не использовать без явной просьбы пользователя:
   сжигает кредиты и токены на страницах, которые не нужны.

Точные команды и флаги — `references/firecrawl-cheatsheet.md`.

## Обязательный workflow кэша

1. До поиска — прочитать `research/INDEX.md`.
2. Результат — сразу в файл `research/<тема-slug>_<YYYY-MM-DD>.md`:
   - поисковые запросы;
   - источники: URL + дата публикации (материалу про «современный
     Python» старше ~2 лет не доверять без перепроверки);
   - **выжимка сверху** — то, ради чего искали;
   - сырьё (полные тексты) — в конец, и только если оно понадобится
     повторно; иначе не хранить.
3. Обновить строку в `INDEX.md` (тема, дата, TTL — правила там).
4. В чат — только выжимку и вывод. Сырьё в контекст не тащить: писать
   вывод Firecrawl через `-o` сразу в файл и читать оттуда выборочно.

## Типовые сценарии

- **Материалы нового этапа roadmap** (ООП, Git, SQL, pytest, FastAPI…):
  чем учить тему в текущем году, какие курсы/книги/доки живы, что
  устарело. Рынок ученика — РФ: смотреть и русскоязычные ресурсы
  (Stepik, Хабр, hh.ru). Итог: 1-2 рекомендации + запись в кэш +
  предложить правку roadmap в `study_python/CLAUDE.md`.
- **Пополнение банка задач**: реальные вопросы и тестовые задания с
  собеседований junior Python backend (РФ). Искать **сюжеты**, не готовые
  задачи — калибровку под уровень делает coach-skill по known_topics.md.
  Итог: предложить новые сценарии в
  `coach-skill/references/task-design.md` (вносить после подтверждения).
- **Тренды** («что сейчас актуально», ежемесячный запуск) — методика и
  запросы в `coach-skill/references/trends.md`; этот skill даёт
  инструментальную часть (порядок инструментов, кэш).
- **Релизы/breaking changes** конкретного инструмента — сначала `gh`
  (п. 2), Firecrawl только если changelog живёт вне GitHub.

## Экономия кредитов и токенов

- Текущий год в запросах — из окружения сессии, не из памяти модели.
- `search --limit 3-5`; `scrape` точечно; повторный scrape того же URL —
  с `--max-age` (отдаётся из кэша Firecrawl, дешевле и быстрее).
- Один сеанс исследования — одна тема. Не смешивать.
- Баланс кредитов: `firecrawl credit-usage`.
- Ключ — переменная окружения `FIRECRAWL_API_KEY` (на ПК настроена
  2026-07-15; на Mac настроить при первом использовании: тот же ключ,
  `export` в профиль шелла). Ключ в репозиторий не коммитить.
