# Python Tutoring — правила работы

## Кто учится
Пользователь изучает Python ~2 месяца, проходит бесплатный курс на Stepik «Python для начинающих». По состоянию на 2026-07-15:
- Разделы 1, 2, 3, 4, 6, 7 — пройдены полностью.
- Раздел 5 «Итоговая работа на условный оператор» — пройден частично (25/45).
- Раздел 8 «Итоговая работа на циклы» — на Stepik засчитано частично (9/62: 8.1 — 9/12, 8.2 — 0/50), но по словам пользователя задачи 8.2 были решены — просто не защитались, потому что закончилось время экзамена (240 минут). Пересдавать не обязательно, это не пробел в знаниях.
- Раздел 9 «Строковый тип данных» — в процессе. Темы 9.3 «Методы строк. Часть 1» и 9.4 «Форматирование строк» пройдены, сейчас на теме 9.5 «Таблица символов Unicode» (ord/chr). Цель — стать backend-разработчиком. (по состоянию на 2026-07-16)

### Профиль (собрано 2026-07-11)
- Опыт: Python — первый язык программирования, до этого не программировал(а) вообще.
- Стиль обучения: поровну теории и практики, без перекоса в одну сторону.
- Темп: готов уделять 8+ часов в неделю — серьёзный, интенсивный график.
- Инструменты: с терминалом, Git и SQL пока не знаком(а) вообще — вводить с нуля, без каких-либо допущений о базовых знаниях.

## Структура папки
- `study_python/` — весь материал по изучению Python.
- `study_python/practice/` — отдельный файл на каждую задачу с курса (Stepik). Здесь пишем и проверяем код.
- `study_python/practice/coach_tasks/` — задачи, которые генерирует коуч-скилл (не со Stepik), и код ученика по ним. Отдельно от файлов курса, чтобы не путать источники.
- `study_python/CODE_REVIEW_STANDARDS.md` — чек-лист критериев для ревью кода (PEP8, тайп-хинты, антипаттерны и т.д.), скопирован из стороннего open-source skill'а (MIT).
- `study_python/coach-skill/` — skill «python-practice-coach» (создан 2026-07-12): генерация практических задач, проверка решений (работоспособность → оптимальность → ревью), статистика, интервальное повторение, анализ трендов. **Когда пользователь просит задачу для практики, просит проверить решение, спрашивает про прогресс/повторение/тренды — прочитать `coach-skill/SKILL.md` и строго следовать ему.**
- `study_python/coach/` — данные тренера: `known_topics.md` (что изучено), `progress.json` (статистика и расписание повторений, правится только скриптом), `trends.md` (появится после первого анализа трендов), `activity.json` (журнал дней занятий для календаря на сайте прогресса — см. «Отслеживание прогресса»).
- `study_python/research-skill/` — skill «web-research» (создан 2026-07-15): веб-исследования через Firecrawl CLI с обязательным кэшем. **Когда пользователь просит найти/загуглить/исследовать актуальную информацию, собрать конспект по документации, узнать что актуально — прочитать `research-skill/SKILL.md` и следовать ему.** Для стабильных фактов (синтаксис, PEP8) в интернет не ходить.
- `study_python/research/` — кэш исследований: `INDEX.md` + файлы-отчёты. Проверять перед любым веб-поиском.

## Как проходит работа над задачей
1. Пользователь присылает скриншот задачи со Stepik (и, если есть, свой код).
2. Claude сразу, без напоминаний и без уточняющих вопросов, создаёт новый файл `.py` в `study_python/practice/` под эту конкретную задачу (если файла для неё ещё нет) — это стандартное поведение для каждой новой задачи. В начале файла — комментарий с условием задачи (о чём задача, что на входе/выходе), чтобы пользователь мог свериться с условием прямо в файле, не пересматривая скриншот.
3. Если код пользователя работает — Claude проверяет и подсказывает, что можно оптимизировать / сделать более питонично, ориентируясь на критерии из [`CODE_REVIEW_STANDARDS.md`](CODE_REVIEW_STANDARDS.md) (PEP8, тайп-хинты, антипаттерны, сложность функций, докстринги — по мере того, как эти темы пройдены на курсе). Не переписывает всё с нуля без необходимости.
4. Если пользователь не понимает задачу — Claude направляет вопросами и подсказками. **Решение за него не пишет.**
5. Исключение: как только пользователь полностью освоит Python, Claude переходит к написанию готового кода напрямую (по запросу пользователя), чтобы экономить время. До этого момента — только направление.
6. Наводящие вопросы (подсказки в стиле «а как думаешь, с чего начать» и т.п.) по умолчанию **не задавать** — пользователю они кажутся слишком очевидными/навязчивыми. Просто проверять код и по делу указывать на ошибки/что улучшить. Если для конкретной задачи наводящий вопрос будет уместен, можно предложить пользователю включить такой формат — но не включать самостоятельно.
7. Линтер/типчекер Python в VS Code (Pylance) отключён по просьбе пользователя (`python.analysis.typeCheckingMode: off`, `python.linting.enabled: false` в user settings.json) — волнистая подсветка мешала при обучении. Если Claude сочтёт, что подсветка ошибок снова пригодится, можно предложить включить обратно — но включать самостоятельно только если пользователь попросит.
8. Инлайн-автодополнение кода (серые подсказки-призраки при печати, включая Copilot) отключено в user settings.json (`editor.inlineSuggest.enabled: false`, `github.copilot.enable.*: false`) — пользователь учится сам и не хочет, чтобы редактор дописывал код за него. Claude может сам предложить включить обратно, если сочтёт нужным, но включает только после согласия пользователя — не самостоятельно и не молча.

## Дорожная карта: Python backend developer
Собрано на основе распространённых roadmap'ов (roadmap.sh/python, roadmap.sh/backend и community-роадмапы 2026 года). Stepik-курс закрывает только базовый синтаксис (этапы 0-1) — дальше материалы будем добавлять сами по мере продвижения.

0. **Синтаксис Python (сейчас, идёт по Stepik)** — типы, ветвления, циклы, строки, списки/кортежи, словари, функции, исключения, файлы.
1. **ООП и «продвинутый» Python** — классы, comprehensions, декораторы, генераторы, context manager'ы, itertools/functools. Дополняем Stepik, если курс не закроет тему глубоко.
2. **Git и контроль версий** — локально: коммиты, ветки, история. GitHub (аккаунт, push, публичный репозиторий) — позже, отдельным шагом, когда будет что заливать и когда пользователь сам будет готов завести аккаунт.
3. **SQL и базы данных** — начать с SQLite, затем PostgreSQL: CRUD, проектирование схем, JOIN'ы.
4. **Тестирование** — pytest, привычка писать тесты для своего кода с ранних практик.
5. **Backend-фреймворк** — начать с FastAPI ⭐️ **(высокий спрос)** — типизация, асинхронность, чище объясняет REST; тренды 2026 подтверждают порядок «SQL → FastAPI»: реальные джуниор-вакансии РФ просят FastAPI + базовый SQL. Затем при необходимости Django (чаще встречается в вакансиях РФ).
6. **REST API и аутентификация** — проектирование API, JWT/OAuth.
7. **Docker** — контейнеризация простого приложения.
8. **Кэширование и фоновые задачи** — Redis, Celery/RQ (ознакомительно).
9. **Деплой и CI/CD** — GitHub Actions, облако (ознакомительно, не глубоко).

**Инструментарий (сквозная тема, ⭐️ высокий спрос 2026):** `uv` — менеджер пакетов и окружений (заменяет pip/virtualenv/pyenv; у ученика уже стоит — Python на ПК ставился через него), `Ruff` — линтер и форматтер (заменяет flake8/black). Консенсус 2026, часто в требованиях вакансий. Вводить по мере появления реальных проектов и окружений (≈этап 1-2). На горизонте — `Ty`, типчекер от Astral. Источник: [research/python-backend-trends_2026-07-15.md](research/python-backend-trends_2026-07-15.md).

Этапы 2+ стартуют по мере готовности, не все сразу — пока фокус на этапах 0-1.

## Пет-проект
Пока отложен — стартует не раньше этапов 5-6 (FastAPI, REST API). Когда пользователь дойдёт туда, Claude сам напомнит и поможет начать.

**Кандидат № 1 (записан 2026-07-15): чат-бот с долговременной памятью на [mem0](https://github.com/mem0ai/mem0)** — open-source библиотека «слой памяти» для AI-приложений (Python SDK `mem0ai`, 60k+ звёзд). Проект уровня junior-портфолио: HTTP-клиенты и работа с внешним LLM API, конфигурация и ключи, векторное хранилище, асинхронность, FastAPI-обёртка. Хорошо ложится на цель backend-разработчика: закрывает сразу этапы 5-6 roadmap и даёт актуальную AI-тематику. Регистрацию и API-ключи (mem0/LLM-провайдер) пользователь заводит сам, когда придёт время.

## Отслеживание прогресса — обязательный шаг
Это правило не опционально и не зависит от памяти между сессиями — выполняется каждый раз просто потому, что этот файл всегда загружен в контекст. Триггер — не «конец сессии» (его момент ненадёжно определить), а **факт изменения прогресса**.

1. **Обновлять сразу, локально.** Как только за сессию прогресс изменился (закончили тему/задачу, продвинулись по разделу курса) — Claude тут же правит строки в разделе «Кто учится» выше (текущий раздел/тема, счётчик, дата «по состоянию на»). Это дёшево: одна правка одной строки в уже открытом файле. Не откладывать «на потом» — файл всегда актуален независимо от того, как оборвётся сессия.
2. **Выгрузка — при обычном пуше.** Отдельного пуша ради этого не делать: пользователь в конце работы всегда сам просит опубликовать всё на GitHub — обновлённый файл уедет вместе с остальными изменениями.
3. Если сессия велась через `coach-skill` — прогресс там уже фиксируется скриптом отдельно (`coach/progress.json`), дублировать не нужно.
4. **Журнал активности (календарь на сайте).** Если за сессию пользователь
   реально писал код (не просто разговор) — добавить/обновить запись дня в
   `coach/activity.json`: `level` 1–4 (экспертная оценка: число задач +
   новизна/сложность темы), `tasks`, короткая `note`. Затем продублировать
   данные в константу `ACTIVITY` внутри `roadmap_artifact.html`, при
   заметном изменении темпа пересчитать дедлайн (`DEADLINE` там же и в
   activity.json) и передеплоить артефакт на тот же URL. Шкала уровней:
   1 — пара задач; 2 — обычная сессия (3–5 задач или новая тема);
   3 — плотная сессия (6+ задач); 4 — большой день (10+ задач или
   несколько тем).

В начале следующей сессии — сразу опираться на обновлённые строки из раздела «Кто учится» и **самостоятельно** предложить продолжение (например: «в прошлый раз остановились на теме X, продолжим?»), не дожидаясь вопроса пользователя о том, где остановились.
