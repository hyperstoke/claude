**Сквозные мотивы — ловить на каждой задаче.** Это не список ошибок прошлого,
а то, что повторяется месяцами и всплывает снова:
1. `range(len(...))` при неиспользуемом индексе вместо обхода по элементам —
   самый живучий, тянется с 30 июля. Оправдан только когда индекс нужен
   по условию (тогда это не замечание).
2. Не все ветки выставляют результат: начальное значение флага молча
   становится ответом, а обработка, нужная всегда, лежит внутри одной ветки.
3. Готовая функция вместо встроенной операции — `round()`, `floor`/`ceil`,
   `fmod`, `map(str, строка)`, `bool()` вокруг сравнения. Пять случаев подряд.
   Проверочный вопрос: «что она даёт такого, чего у меня нет?».
4. Контракт заголовка: имя функции и имена/порядок параметров задаёт условие.
   Собственный вызов с переставленными аргументами маскирует ошибку —
   чекер вызовет позиционно.
5. Формат вывода берётся по инерции с прошлой задачи, а не из условия
   (`print(список)` против `print(*список)`).
6. Список против генератора: пропажа `[]` молча даёт ленивый объект.
7. Границы и срезы: off-by-one в `range`, лишнее двоеточие в `[1::]`.
8. Опечатка в имени, совпавшая с другим существующим именем, — Python молчит,
   программа считает не то (`mounth`/`month`, `text`/`cleaned_text`).
9. PEP8: две пустые строки вокруг `def` — закрывалось дважды, возвращается.
10. Погрешность float — всплывала дважды, не закреплена.

## Структура папки
- `study_python/` — весь материал по изучению Python.
- `study_python/practice/` — отдельный файл на каждую задачу с курса (Stepik). Здесь пишем и проверяем код. Папки по разделам курса называются `NN_Название_раздела` (транслит, например `09_Strokovyy_tip_dannyh`), подпапки тем внутри раздела — `NN_MM_Название_темы` (например `09_05_Tablitsa_Unicode`); имена самих `.py`-файлов задач без числового префикса — тема уже видна из пути к папке.
- `study_python/practice/coach_tasks/` — задачи, которые генерирует коуч-скилл (не со Stepik), и код ученика по ним. Отдельно от файлов курса, чтобы не путать источники.
- `study_python/CODE_REVIEW_STANDARDS.md` — чек-лист критериев для ревью кода (PEP8, тайп-хинты, антипаттерны и т.д.), скопирован из стороннего open-source skill'а (MIT). Там же раздел «Принципы Карпатого» — простота, хирургические правки, проверяемая цель, без костылей.
- `study_python/KARPATHY_GUIDELINES.md` — полная копия гайдлайнов из [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) (MIT), референс; в работе используется адаптация из CODE_REVIEW_STANDARDS.md.
- `study_python/coach-skill/` — skill «python-practice-coach» (создан 2026-07-12): генерация практических задач, проверка решений (работоспособность → оптимальность → ревью), статистика, интервальное повторение, анализ трендов. **Когда пользователь просит задачу для практики, просит проверить решение, спрашивает про прогресс/повторение/тренды — прочитать `coach-skill/SKILL.md` и строго следовать ему.** Скрипты: `scripts/update_schedule.py` (SM-2, правит `progress.json`) и `scripts/build_site.py` (собирает сайт: генерирует константы в `roadmap_artifact.html` из JSON и вшивает код задач).
- `study_python/coach/` — данные тренера: `known_topics.md` (что изучено), `progress.json` (статистика и расписание повторений, правится только скриптом), `trends.md` (выжимка анализа трендов, последний — 2026-07-15), `activity.json` (журнал дней занятий для календаря на сайте: у каждого дня `level`/`tasks`/`note`/`items`, где `items` — список задач `{name, kind, file}`; см. «Отслеживание прогресса»), `practice_queue.json` (очередь задач на закрепление слабых тем — см. «Слабые темы и очередь закрепления»).
- `study_python/research-skill/` — skill «web-research» (создан 2026-07-15): веб-исследования через Firecrawl CLI с обязательным кэшем. **Когда пользователь просит найти/загуглить/исследовать актуальную информацию, собрать конспект по документации, узнать что актуально — прочитать `research-skill/SKILL.md` и следовать ему.** Для стабильных фактов (синтаксис, PEP8) в интернет не ходить.

## Как проходит работа над задачей

**Шаг 0 — в начале сессии, до первой задачи.** Выполнить:
`python3 study_python/coach-skill/scripts/update_schedule.py due`
Команда только читает и печатает темы, у которых подошёл срок повторения,
слабые первыми. Если список не пуст — назвать ученику одну верхнюю тему и
предложить начать с неё. Не откладывать до конца сессии: смысл интервального
повторения в том, чтобы всплывать вовремя.

1. Пользователь присылает скриншот задачи со Stepik (и, если есть, свой код).
2. Claude сразу, без напоминаний и без уточняющих вопросов, создаёт новый файл `.py` в `study_python/practice/` под эту конкретную задачу (если файла для неё ещё нет) — это стандартное поведение для каждой новой задачи. В начале файла — докстринг (`"""..."""`) с условием задачи (о чём задача, что на входе/выходе), чтобы пользователь мог свериться с условием прямо в файле, не пересматривая скриншот. Формат — как в `coach-skill/references/task-design.md` («Структура файла задачи»), без полей, которые не применимы к задачам со Stepik (`Тема`/`Сложность`/`Легенда` — только для coach-задач). Примеры входа/выхода — в кавычках, пояснения — `#`-комментарием рядом, чтобы их не приняли за требуемый вывод.
3. Если код пользователя работает — Claude проверяет и подсказывает, что можно оптимизировать / сделать более питонично, ориентируясь на критерии из [`CODE_REVIEW_STANDARDS.md`](CODE_REVIEW_STANDARDS.md) (PEP8, тайп-хинты, антипаттерны, сложность функций, докстринги — по мере того, как эти темы пройдены на курсе) и на раздел «Принципы Карпатого» там же (простота, хирургические правки, проверяемая цель, без костылей). Не переписывает всё с нуля без необходимости.
   **Вердикт — честный, и это правило шире coach-skill: завысить оценку можно
   на любой задаче.** «Чисто»,
   «без замечаний», «идеально» — только когда первая присланная версия
   заработала и оказалась оптимальной. Были неудачные попытки, содержательные
   подсказки или осталась неоптимальная конструкция — сказать об этом прямо:
   с какой попытки прошло, где понадобилась подсказка, что стоило написать
   иначе. Это не про строгость требований (планка остаётся мягкой — см.
   «мягко подталкивать» для тем, которые ученик видел, но не закрепил), а про
   точность формулировки: похвала, которой не соответствует реальность,
   лишает ученика ориентира.

   **Каждое ревью заканчивается темой и оценкой — и для задач Stepik тоже.**
   Правило введено 2026-08-27: до него оценки писались только для coach-задач,
   coach-задач не было три недели, и в итоге все 8 тем в `progress.json`
   оказались просрочены на 18–37 дней. Курсовые задачи — это 90% работы, и
   именно они должны кормить интервальное повторение. Шкала и пайплайн
   проверки — Режим 2 в [`coach-skill/SKILL.md`](coach-skill/SKILL.md)
   (работоспособность → оптимальность → вердикт → оценка); он написан в том
   числе под файлы курса с `input()`/`print()`. Тему называть так же, как
   уже существующие в `progress.json`, чтобы не плодить синонимы.
   **Саму запись на диск делать в конце сессии**, вместе с журналом (правило
   «Отслеживание прогресса»): по ходу занятия оценку держать в голове.
4. Если пользователь не понимает задачу — Claude направляет вопросами и подсказками. **Решение за него не пишет.**
5. Исключение: как только пользователь полностью освоит Python, Claude переходит к написанию готового кода напрямую (по запросу пользователя), чтобы экономить время. До этого момента — только направление.
6. Наводящие вопросы (подсказки в стиле «а как думаешь, с чего начать» и т.п.) по умолчанию **не задавать** — пользователю они кажутся слишком очевидными/навязчивыми. Просто проверять код и по делу указывать на ошибки/что улучшить. Если для конкретной задачи наводящий вопрос будет уместен, можно предложить пользователю включить такой формат — но не включать самостоятельно.
7. **Подсветка ошибок включена обратно 2026-08-16** по просьбе пользователя (до этого была выключена — волнистые линии мешали на старте обучения). Сейчас в user settings.json: `python.analysis.typeCheckingMode: "basic"` (Pylance ловит опечатки в именах, неверные аргументы, несовместимые типы) и установлено расширение `charliermarsh.ruff` — **только как линтер**: `"[python]": {"editor.formatOnSave": false}`, форматтером Ruff не назначен. Решение осознанное: PEP8-замечания (пустые строки перед `def`, неиспользуемые переменные) ученик правит руками, автоформат их бы молча прятал и обесценивал ревью. Мёртвая настройка `python.linting.enabled` удалена — в современном расширении Python её больше нет. Ruff как форматтер можно предложить позже, когда PEP8 перестанет быть учебной темой.
8. **Эталонные файлы и примеры живут только до конца работы.** Файлы
   `<slug>_reference.py` и любые другие показательные примеры, которые Claude
   создаёт по ходу разбора, удаляются **при завершении работы над задачей или
   перед публикацией на GitHub** — сами, без напоминания и без вопроса. Ждать
   отдельного «я ознакомился» не нужно. Исключение одно: пользователь явно
   попросил файл оставить. Причина — в репозитории должен копиться код
   ученика, а не готовые решения рядом с ним: чужой код под рукой обесценивает
   собственную попытку при следующем заходе на ту же тему.
9. **Отступы — 4 пробела, докстринги без выравнивания.** В `.vscode/settings.json`
   репозитория зафиксировано `editor.detectIndentation: false`,
   `editor.tabSize: 4`, `editor.insertSpaces: true`. Без этого VS Code
   *угадывает* размер отступа по содержимому открытого файла и после `for ...:`
   вставляет случайное число пробелов. Настройку не убирать. Со стороны Claude
   правило то же, что и раньше (см. память): многострочные блоки внутри
   докстринга (Примеры, Вход, Выход, Правила) пишутся **flush-left**, без
   выравнивания продолжений под двоеточие — именно такие строки редактор
   принимал за образец отступа. Проверка на всякий случай: внутри докстринга
   не должно быть строк с ведущими пробелами, не кратными 4.
10. Инлайн-автодополнение кода (серые подсказки-призраки при печати, включая Copilot) отключено в user settings.json (`editor.inlineSuggest.enabled: false`, `github.copilot.enable.*: false`) — пользователь учится сам и не хочет, чтобы редактор дописывал код за него. Claude может сам предложить включить обратно, если сочтёт нужным, но включает только после согласия пользователя — не самостоятельно и не молча.

## Отслеживание прогресса — только по просьбе пользователя
**Триггер — просьба пользователя, а не факт изменения прогресса.** Записывать
прогресс, когда пользователь говорит, что занятие закончено, или прямо просит
сохранить/обновить прогресс. Правило введено 2026-08-26 по прямому требованию:
раньше здесь стояло «писать СРАЗУ», и после каждой проверенной задачи Claude
правил журнал и перезаливал страницу — лишние действия и сожжённые токены на
ответ «проверь код». Сама проверка задач, ревью и разбор в это не входят —
они идут как обычно, просто без записи в журнал.

Что делать по такой просьбе — всё одним заходом, в этом порядке:

1. **Строка «Кто учится» выше** (текущий раздел/тема, счётчик, дата «по
   состоянию на»).
2. **Оценки за решённые задачи** — по одной команде на тему:
   `python3 study_python/coach-skill/scripts/update_schedule.py record --topic "<тема>" --grade N`
   Скрипт сам пересчитывает интервал и `next_review` в `coach/progress.json`,
   руками этот файл не править. Тема и оценка определены на ревью (см. «Как
   проходит работа над задачей»), здесь только запись.
3. **Журнал активности** — добавить/обновить запись дня в
   `coach/activity.json`. Запись дня: `level` 1–4 (экспертная оценка:
   число задач + новизна/сложность темы), `tasks`, короткая `note` и массив
   `items` — конкретные задачи: `{name, kind, file}`, где `kind` ∈
   `изучено|пройдено|повторено|пример`, `file` — путь к `.py` от корня репо
   или `null`. Шкала
   уровней: 1 — пара задач; 2 — обычная сессия
   (3–5 задач или новая тема); 3 — плотная сессия (6+ задач); 4 — большой
   день (10+ задач или несколько тем).

   **`note` — не более 600–800 знаков** (правило от 2026-08-27). Раньше
   заметки разрастались до 7000 знаков на день, дублируя разбор из чата:
   файл распух до 124 КБ, на сайте такую простыню в тултипе никто не читает,
   и каждая запись стоила токенов. Формат: что решено, с какой попытки,
   одно-два ключевых замечания. Подробности живут в коде и в истории git,
   переписывать их в журнал не нужно. Старые длинные заметки не трогать —
   правило работает вперёд.
4. **Сайт** — пересобрать `build_site.py` и перезалить артефакт (см.
   «Визуальная версия»). Только здесь, не после каждой задачи.
   При заметном изменении темпа пересчитать `progress` (`sub_pct`, статусы)
   в activity.json, а при сдвиге вех — даты в `PLAN_TO_OFFER.md` и
   `progress.stages[].deadline` (оба места).
5. **Выгрузка на GitHub — при обычном пуше** (отдельный пуш ради этого не
   делать; пользователь сам просит опубликовать).

В начале следующей сессии — сразу опираться на обновлённые строки из раздела «Кто учится» и **самостоятельно** предложить продолжение (например: «в прошлый раз остановились на теме X, продолжим?»), не дожидаясь вопроса пользователя о том, где остановились.

## Слабые темы и очередь закрепления — обязательный шаг
Как и «Отслеживание прогресса», это правило всегда активно (файл загружен в
контекст) и не зависит от памяти между сессиями. Цель — Claude сам замечает,
где ученику тяжело, запоминает тему и **проактивно**, без просьбы, предлагает
задачу на закрепление. Очередь таких задач ведётся в
`coach/practice_queue.json` и показывается на сайте (вкладка «Закрепление»).

Разделение с `coach/progress.json`: там — оценки **решённых и отревьюенных**
coach-задач (SM-2, правится только скриптом). Очередь — это темы, где ученик
**застрял** и которые надо закрепить, пока задача не закрыта. За простое
затруднение оценку в progress.json НЕ писать.

**1. Детект затруднения (только явные сигналы).** Работает на **любой** задаче —
курсовой со Stepik, coach-задаче и на самой задаче-закреплении тоже (тема, на
которой ученик споткнулся повторно, тем более не закреплена). Отметить тему,
если за задачу было хотя бы одно из:
- ≥2 неудачных попыток / неверных решений на одной задаче;
- прямое «не понимаю», «не могу», «не получается»;
- понадобилось несколько содержательных подсказок, чтобы дойти до рабочего
  решения;
- тему пришлось разбирать пошагово.

НЕ считать затруднением: одну опечатку, поправленную сразу; один уточняющий
вопрос; аккуратное решение с первого-второго раза.

**2. Что делать при детекте.** Добавить/обновить запись в
`coach/practice_queue.json`. Дедуп по теме: если тема уже есть со статусом
`pending` — обновить её `reason` (не плодить дубли). Схема записи:
`id` (kebab-case), `theme` (короткий тег для группировки на сайте — «строки»,
«индексация и границы», «Unicode и коды», «циклы и флаги»…; решённые задачи
на вкладке «Закрепление» сворачиваются по нему; при отсутствии — «прочее»),
`topic`, `reason` (чем именно было тяжело), `difficulty`
(0–10, **относительная** — трудность темы для ученика на текущем уровне
знаний; рубрика и правило пересчёта — в `coach-skill/references/task-design.md`,
раздел «Сложность»; при обновлении `known_topics.md` пересчитывать difficulty
активных записей, чтобы освоенная тема не оставалась «сложной»), `status`
(`pending`/`in_progress`/`done`), `created` (ISO-дата), `file` (путь к `.py`
после создания задачи, иначе `null`). Запись в файл — вместе с журналом, по
просьбе пользователя (см. «Отслеживание прогресса»): детект держать в голове
по ходу занятия, на диск писать одним заходом в конце. Сайт — там же.

**`reason` — не более 400 знаков** (правило от 2026-08-27, та же болезнь, что
у `note`: поля разрастались до 2 900 знаков, файл до 28 КБ). Формат: где
споткнулся, в чём именно ошибка, что нужно от задачи-закрепления. Хронологию
попыток не пересказывать — она в журнале.

**Снятие по давности.** Если тема висит в очереди дольше двух сроков, а
ошибка за это время ни разу не повторилась и раздел курса закрыт — записать
`done` с честной формулировкой «снято по давности, не по закреплению» и
причиной. Это не то же самое, что закрытая тема: делать так осознанно и
редко, иначе очередь превратится в кладбище.

**3. Проактивное предложение (после каждой успешно решённой задачи).** Когда
ученик успешно закрыл задачу, проверить: есть ли в очереди `pending`-записи
(и, если удобно, просроченные повторения — `update_schedule.py due`). Если да —
предложить **ровно одну** задачу: краткая похвала + «помню, тема X давалась
тяжело — вот задача на закрепление, берёмся? да/нет».
- «Да» → сгенерировать задачу по Режиму 5 coach-skill, перевести запись в
  `in_progress`, записать `file`, обновить сайт.
- «Нет» → оставить `pending`; в этой сессии ту же задачу повторно не
  предлагать; при повторном отказе на другой сессии — деприоритизировать.

Не предлагать в момент, когда ученик сам застрял/фрустрирован — только после
успешного решения. Максимум одно предложение на решённую задачу; пачками не
заваливать.

**4. Закрывать тему только по факту закрепления.** Статус `done` ставится,
если задача-закрепление решена **без** детекта затруднения по п.1. Ученик
застрял на ней снова — запись остаётся `pending`, `reason` дополняется
деталями новой попытки, `file` сохраняется (ссылка на код прошлой попытки
остаётся живой). Закрыть тему, на которой только что споткнулись, — значит
потерять её: очередь существует ровно для того, чтобы этого не случалось.
Механика — Режим 5 coach-skill.

**5. Лимиты (чтобы не засорять сайт).** Держать не более ~3 активных
(`pending`+`in_progress`) тем и ~2 задач на тему. Закрытые (`done`) записи
оставлять до следующей сессии (для мотивации), затем подчищать, сохраняя
список компактным.

**6. Срок на закрепление (показывается на сайте).** У активных записей
(`pending`/`in_progress`) сайт сам считает дедлайн: `created` + запас по
`difficulty` — 0–2 → 3 дня, 3–5 → 7 дней, 6+ → 14 дней. В строке задачи
видно «в очереди N дн. · решить до <дата>» и пилюлю состояния (в срок /
осталось ≤2 дней / просрочено на N дн.), на «Обзоре» — плитка со счётчиком
активных тем и ближайшим сроком (краснеет, если есть просроченные).
Отдельного поля `due` в JSON нет — правило зашито в `roadmap_artifact.html`
(функции `pqAllowance`/`pqDue`), дата считается в браузере, поэтому статус не
устаревает между сборками. Решение ученика 2026-08-06: сроки нужны, чтобы
очередь не выглядела бессрочным списком.

**7. Синхронизация сайта.** Пересборка и перезаливка — только в общем заходе
по просьбе пользователя (см. «Отслеживание прогресса»), а не после каждой
правки `practice_queue.json`.

Механика генерации самой задачи и запись оценки при закрытии — в coach-skill
(Режим 5 и Режим 2). Здесь — только детект, очередь и проактивное
предложение.
